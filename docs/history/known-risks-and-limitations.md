# Known Risks and Limitations

This document records verified EvolvePHP 1 risks and limitations at audited commit `2da5da7866f65d314a0e2bf10b572004b3014d60`. The findings below are documentation only; they were not repaired in Phase 0.

EvolvePHP 1 is not recommended as the starting point for a new production application without a detailed security, compatibility and maintainability review. New production work should prefer the separate EvolvePHP 2 redesign once it is available and reviewed.

## Risk register

| Issue | Classification | Evidence | Description | Potential impact | Current status | Ownership |
| --- | --- | --- | --- | --- | --- | --- |
| Arbitrary CORS-origin reflection | Security | `index.php` reflects `$_SERVER['HTTP_ORIGIN']` into `Access-Control-Allow-Origin`. | Any supplied origin is echoed when the origin header exists. | Cross-origin browser access may be broader than intended. | Preserved legacy behaviour. | EvolvePHP 1 maintenance only if a legacy security task is opened; otherwise EvolvePHP 2 redesign. |
| Credentialed CORS behaviour | Security | `index.php` sends `Access-Control-Allow-Credentials: true`. | Credentialed requests are allowed together with reflected origins. | Cookies or authenticated browser state could be exposed to untrusted origins. | Preserved legacy behaviour. | EvolvePHP 1 maintenance for security fix; EvolvePHP 2 needs explicit CORS policy. |
| PHP-version check and message mismatch | Correctness, Documentation | `index.php` checks `< 7.1.0` but tells users PHP 5.4.0 or newer is supported. | Runtime gate and user-facing message disagree. | Operators may deploy unsupported PHP versions or misunderstand requirements. | Documented only. | EvolvePHP 1 maintenance documentation/runtime fix if approved. |
| Debug mode enabled by default | Security, Developer experience | `configs/user.config.php` defines `DEBUG` as `TRUE`. | Development mode is the default in repository config. | Sensitive error details may be displayed if deployed unchanged. | Preserved legacy default. | EvolvePHP 1 maintenance for deployment hardening; EvolvePHP 2 configuration redesign. |
| Incorrect `display_error` production setting | Correctness, Security | `configs/ini.config.php` uses `ini_set('display_error', 0)` in production branch. | PHP's setting is `display_errors`, not `display_error`. | Production error display may not be disabled as intended. | Documented only. | EvolvePHP 1 maintenance if targeted. |
| Boolean versus bitwise error mask | Correctness | `configs/ini.config.php` uses `E_ERROR || E_USER_ERROR || E_COMPILE_ERROR`. | Logical OR produces a boolean-like value instead of the intended bitmask. | Error reporting may not match intended severities. | Documented only. | EvolvePHP 1 maintenance if targeted. |
| Error-log path mismatch | Correctness, Developer experience | `configs/ini.config.php` sets `error_log` to `__DIR__."/logs/php-error.log"`. | From `configs/`, this points to `configs/logs/php-error.log`, while the repo has root `logs/`. | PHP error logs may fail or be written to an unexpected location. | Documented only. | EvolvePHP 1 maintenance if targeted; EvolvePHP 2 logging design. |
| Trust in `HTTP_HOST` | Security | `configs/application.config.php` builds `BASE_URL` from `$_SERVER['HTTP_HOST']`. | Host header is used directly for base URLs and asset URLs. | Host-header spoofing can affect generated links and redirects. | Preserved legacy behaviour. | EvolvePHP 1 maintenance security fix or EvolvePHP 2 request/config design. |
| Direct global-state usage | Maintainability, Compatibility | `index.php`, `route.php`, `configs/*.php`, `helpers/*`, `core/Session.php`. | Runtime behaviour depends directly on superglobals, constants and PHP global state. | Harder testing, reuse, concurrency and persistent-worker execution. | Preserved legacy behaviour. | EvolvePHP 2 redesign. |
| Direct header output | Maintainability, Compatibility | `index.php`, `helpers/Url.php`, `components/error/controllers/ErrorController.php`. | Headers and response codes are emitted directly from multiple locations. | Harder response composition, testing and middleware-style handling. | Preserved legacy behaviour. | EvolvePHP 2 redesign. |
| Dynamic controller and method dispatch | Security, Maintainability | `route.php` instantiates classes from `DEFAULT_ROUTE` and invokes methods based on route segments. | Methods on the default controller can be called dynamically when route segments match method names. | Expands public method surface and complicates route authorization. | Preserved legacy behaviour. | EvolvePHP 1 hardening only if targeted; EvolvePHP 2 router/contracts. |
| Route-file inclusion | Security, Maintainability | `route.php` includes `COMPONENTS_DIR.$erVal.DS.'route.php'` when readable. | Component route files are loaded based on sanitized request segments. | Route behaviour can become difficult to reason about across components. | Preserved legacy behaviour. | EvolvePHP 2 module/router redesign. |
| Absence of request and response abstractions | Maintainability, Compatibility | No request/response classes were found; runtime uses superglobals and direct output. | HTTP state is not represented by explicit framework objects. | Difficult testing, middleware, PSR interoperability and persistent workers. | Existing limitation. | EvolvePHP 2 redesign. |
| Absence of middleware | Maintainability | No middleware layer or pipeline was found. | Cross-cutting concerns are handled inside entry point, router, controllers and helpers. | Auth, CORS, CSRF and logging cannot be composed predictably. | Existing limitation. | EvolvePHP 2 redesign. |
| Absence of dependency injection | Maintainability | Controllers and factories instantiate classes directly with `new`; no container found. | Dependencies are hidden inside classes and factories. | Harder testing, replacement and modularity. | Existing limitation. | EvolvePHP 2 redesign. |
| Legacy PHP runtime support | Compatibility | `composer.json` requires `php >=7.1`; `index.php` checks 7.1. | PHP 7.1 is end-of-life. | Modern package compatibility and security maintenance are constrained. | Preserved baseline. | EvolvePHP 2 runtime policy; EvolvePHP 1 maintenance only if required. |
| Outdated or conflicting dependencies | Compatibility, Maintainability | `composer.json` declares `apache/log4php`, `monolog/monolog:^2.0`, `karelwintersky/monolog-pdo-handler:^0.2.0`, `whichbrowser/parser:^2.0`. | The dependency set mixes logging libraries and old PHP compatibility requirements. | Dependency resolution, support and security posture require review before production use. | Not changed in Phase 0. | EvolvePHP 2 dependency review; EvolvePHP 1 only if maintenance requires. |
| Multiple logging libraries | Maintainability | `core/log/Apachelog4phpFileLogger.php`, `core/log/MonologDatabaseLogger.php`, Composer Monolog packages. | Default logger uses log4php while Monolog database logging is a placeholder. | Confusing extension path and unused dependencies. | Preserved baseline. | EvolvePHP 2 logging redesign. |
| Composer `version` field | Developer experience, Documentation | `composer.json` contains `"version": "1.0"`. | Composer package versions are usually inferred from VCS tags. | May mislead consumers when no matching audited tag exists. | Documented only. | EvolvePHP 1 metadata task if approved. |
| Composer `serve` command correctness | Developer experience, Correctness | `composer.json` script is `php -S 0.0.0.0:8800 -t /index.php`. | PHP's built-in server `-t` expects a document-root directory, not an entry-point file path. | Local serving through Composer may fail or serve the wrong root. | Documented only. | EvolvePHP 1 maintenance if targeted. |
| Test coverage limitations | Maintainability | `tests/` contained only `tests/index.html`; no PHPUnit XML found. | There was no meaningful automated test suite before Phase 0 policy tests. | Regressions are hard to detect. | Documentation-policy tests added in Phase 0; runtime coverage remains limited. | EvolvePHP 1 tests for maintenance; EvolvePHP 2 TDD. |
| Environment-specific assumptions | Compatibility | Timezone forced to `Africa/Lagos`; Apache `.htaccess`; `getallheaders()`; `$_SERVER` fields. | Runtime assumes specific server variables and deployment behaviour. | Portability issues across servers, CLIs and workers. | Preserved baseline. | EvolvePHP 2 environment abstraction. |
| Apache rewrite dependency | Compatibility, Developer experience | `.htaccess` rewrites all non-file routes to `index.php?route=$1`; README notes Apache deployment. | Routing depends on compatible rewrite configuration. | Non-Apache deployments require manual equivalents. | Preserved baseline. | EvolvePHP 2 front-controller/server docs. |
| Session security and fingerprinting behaviour | Security, Scalability | `core/Session.php` binds sessions to `REMOTE_ADDR` and browser parser output; uses `md5(rand())` for CSRF token. | Session validity depends on IP/browser fingerprint and weak token generation. | Mobile networks, proxies or browser changes may break sessions; CSRF token entropy is weak. | Documented only. | EvolvePHP 1 security maintenance if targeted; EvolvePHP 2 session/security design. |
| Database abstraction and query-building risks | Security, Maintainability | `core/Model.php` concatenates table names, columns, joins, where keys and extra SQL. | Values are parameterized in several paths, but identifiers and fragments are accepted as strings/arrays. | SQL-injection risk if untrusted identifiers/fragments reach these helpers; limited portability. | Preserved baseline. | EvolvePHP 1 maintenance if exploited; EvolvePHP 2 data-access contracts. |
| Persistent-worker incompatibility | Compatibility, Scalability | Global constants, superglobals, sessions, static factory patterns and direct output are used throughout. | Runtime state is not reset through an explicit lifecycle. | Long-running workers may leak request state across requests. | Existing limitation. | EvolvePHP 2 redesign. |
| Horizontal-scaling limitations | Scalability | File logs, PHP sessions, local config constants and direct server state are used. | Runtime lacks documented shared session/logging/cache strategy. | Multiple-server deployments need additional infrastructure design. | Existing limitation. | EvolvePHP 2 cloud-ready architecture. |
| Missing CI | Developer experience, Maintainability | No CI workflow files were found in the audited file list. | Tests and validation are not automatically enforced by repository configuration. | Quality gates rely on manual execution. | Existing limitation. | EvolvePHP 2 governance or repository automation task. |
| Missing formal release and support policy | Documentation, Developer experience | No `SECURITY.md`, `SUPPORT.md` or detailed changelog policy existed before Phase 0. | Users did not have clear vulnerability, support or legacy status guidance. | Ambiguous expectations for maintainers and users. | Addressed by Phase 0 policy docs. | Governance baseline; future updates as support evolves. |

## Scope note

These findings are intentionally not fixed here. Phase 0 preserves the EvolvePHP 1 baseline and documents the evidence needed to guide later EvolvePHP 1 maintenance decisions and EvolvePHP 2 design work.
